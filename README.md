# piifilterc

OpenAI's [privacy-filter](https://github.com/openai/privacy-filter) PII masking
model (1.5B-param MoE, 50M active) reimplemented as one C file, tuned for Apple
Silicon. No dependencies beyond libm; weights are mmap'd bf16 straight out of
`model.safetensors`.

```
$ ./pf "Call Maya Chen at +1 (415) 555-0124 or maya@example.com"
Call <PRIVATE_PERSON> at <PRIVATE_PHONE> or <PRIVATE_EMAIL>
```

Output is byte-identical to the Python reference (`opf --device cpu`) on every
input tested — including windowed long inputs — at ~1,650 tok/s warm on an M2
Air (~65× the reference, ~166 GFLOPS sustained). On SME2 chips (Apple M4 and
later, detected at run time) the default path runs the matmuls on the SME
matrix engine instead, with int8 experts in layers 2-7 — ~8× faster on an M4
Max, near-exact (see [SME2](#sme2-matrix-engine-m4-and-later)); `--exact`
keeps the byte-identical path there.

## What's inside (pf.c, ~1,300 lines)

- **o200k_base tokenizer**: hand-compiled scanner for the pretokenizer regex
  (Unicode tables generated by `gen_unicode.py`), rank-based BPE, bit-exact
  with tiktoken.
- **Forward pass**: 8 pre-norm blocks; GQA (14Q/2KV) with interleaved-pair
  YaRN RoPE; ±128 banded bidirectional attention with log2-space sink logits;
  128-expert top-4 MoE with gpt-oss SwiGLU (clamps, +1 linear bias).
- **Kernels**: weights stay bf16 in the mmap; `BFDOT` (ARMv8.6 bf16 dot
  product) GEMM with pair-interleaved k-tiles reused across 16-token blocks;
  expert work split into `(expert, ≤16 tokens)` chunks dispatched via
  libdispatch to dodge router skew; NEON exp/sigmoid; parallel page pre-touch.
  On SME2, the dense projections, router and layer 0-1 experts run as
  `BFMOPA` outer products, attention as fp32 `FMOPA`, and the layer 2-7
  experts as Hadamard-rotated int8 `SMOPA`, all on weights re-packed at load.
- **Decoding**: fp32 log-softmax → constrained BIOES Viterbi (33 states, the
  shipped calibration biases are all zero) → span merge, UTF-8 snap,
  whitespace trim, per-label overlap discard → `<LABEL>` masking.

## Benchmarks vs OpenAI's bundled tool

Same machine (MacBook Air M2, 8 cores, 24GB), same checkpoint, both on CPU,
**byte-identical outputs**. "Reference" is the `opf` CLI / Python API from
[openai/privacy-filter](https://github.com/openai/privacy-filter) at default
settings (PyTorch CPU path, no `torch.compile`); `pf` timings include its
mmap + page pre-touch load unless noted.

| Workload                                   | reference `opf` | `pf`            | speedup |
|--------------------------------------------|-----------------|-----------------|--------:|
| One email (107 tok), end-to-end            | 7.7 s           | 1.0 s           |    ~8×  |
| One 2,821-token doc, end-to-end            | 80.5 s          | 3.0 s           |   ~27×  |
| Same doc, inference only                   | ~73 s (39 tok/s)| 1.9 s (1,659 tok/s) | ~38× |
| 144 short docs, one API call each (model preloaded) | 252.7 s (0.6 docs/s) | — | |
| 156 short docs, `pf --lines` (one packed forward), end-to-end | — | 3.8 s (41 docs/s) | ~70× |
| Short docs via HTTP server, 32 concurrent clients | n/a (no server) | 55 docs/s | |

Notes: the reference has no batch or server mode, so the many-docs rows
compare its natural usage (one call per document, ~1.75 s each of which is
per-call overhead) against `pf`'s. Load alone: reference ≈ 6.5 s
(torch import + module build) vs `pf` ≈ 0.25 s warm page cache / ~3 s cold.
Forward-only throughput on long inputs is ~1,400–1,550 tok/s (~166 GFLOPS
sustained; the MoE kernel runs at ~86 of a measured ~91 GMAC/s practical
ceiling). Fanless M2 thermals add ±5% on sustained runs. The precision story:
`pf` accumulates in fp32 over the same bf16 weights and rounds activations to
bf16 at matmul inputs exactly where the reference does — Viterbi label
streams, and therefore outputs, matched the reference on every input tested.

## Setup

```sh
make                       # clang -O3 -mcpu=native; needs Apple Silicon for the fast path
mkdir -p model && cd model
curl -LO https://huggingface.co/openai/privacy-filter/resolve/main/original/config.json
curl -LO https://huggingface.co/openai/privacy-filter/resolve/main/original/model.safetensors
python3 -c "import tiktoken,base64; e=tiktoken.get_encoding('o200k_base'); \
  open('o200k_base.tiktoken','wb').writelines(base64.b64encode(t)+b' '+str(r).encode()+b'\n' \
  for t,r in sorted(e._mergeable_ranks.items(),key=lambda kv:kv[1]))"
```

## Usage

```
./pf "text"                # mask PII, print to stdout
./pf -f file               # from file ("-" = stdin), or pipe to stdin
./pf -j "text"             # JSON spans (byte offsets)
./pf --lines -f file       # batch mode: one document per input line, one output line each
./pf --batch N             # token budget per packed batch (default 16384, min = ctx)
./pf --argmax              # per-token argmax instead of Viterbi
./pf --ctx N               # context window (default 4096, matching reference CPU)
./pf --stats               # timing breakdown on stderr
./pf --exact               # on SME2 chips: keep the reference-identical BFDOT path
./pf --no-int8             # on SME2 chips: bf16 experts instead of int8 (see SME2)
./pf --int8                # elsewhere: opt in to approximate int8 experts
./pf --trim trim/w480.mask # approximate: narrower experts, ~1.2x faster (see below)
./pf --calib out.bin       # write per-neuron expert importance stats (for trim.py)
PF_MODEL=/path/to/model    # checkpoint dir (default ./model)
```

Batching packs many documents (and the windows of long documents) into one
flat token stream with per-segment attention bounds and RoPE positions — the
banded attention makes this exact, not an approximation — so a pile of short
docs runs one big forward instead of many small ones. Weights are pre-touched
in parallel and pinned with best-effort `mlock` at load.

## HTTP server

```
./pf --serve 8080 [--batch N] [--ctx N]
```

Loads once, pins weights, then answers on localhost. Each route is an
*adapter*: a JSON-path pattern set naming which string values carry user
text. The response is the request payload, unchanged except those values are
masked — so it drops in front of an LLM API call as a sanitizing proxy step.

```
GET  /health                 -> {"status":"ok"}
POST /redact                 -> masks "text" and "texts[*]"
POST /redact/openai          -> masks messages[*].content (string or parts[].text)
POST /redact/anthropic       -> masks system / system[*].text / messages[*].content
```

```sh
curl -s localhost:8080/redact/anthropic -d '{
  "model":"claude-fable-5",
  "messages":[{"role":"user","content":"my api key is sk-live-99fKq2"}]}'
# -> ... "content":"my api key is <SECRET>" ...
```

All text fields in one request are masked in a single packed forward, and
concurrent requests are **dynamically batched**: connection threads tokenize
and enqueue, a batcher thread drains the queue after a linger window
(`--linger MS`, default 8) and runs one forward over everything in flight.
At 32 concurrent single-doc clients this roughly doubles throughput over
sequential handling (~29 → ~55 docs/s on an M2 Air) with identical outputs;
solo-request latency pays only the linger. Adding a format = one row in the
`ADAPTERS` table (route + path patterns).

## SME2 matrix engine (M4 and later)

On chips with SME2 the expert GEMMs, the QKV / attention-output projections
and the router run as `BFMOPA` outer products (16 tokens × 64 outputs per
pass, fp32 accumulation in ZA tiles); the experts of layers 2-7 run in int8
instead (`SMOPA`, see [int8 experts](#int8-experts)). Weights are re-packed
at load (+0.15 s; the mmap'd originals are unpinned, so RSS doesn't double).
Attention runs on SME too, in fp32 (`FMOPA`): per 16-query block and head,
Sᵀ = K Qᵀ over the block's union key window, a masked softmax vectorized
across the 16 queries on NEON (no `exp` in streaming mode), then O = P V.
Norms, SwiGLU and top-k stay on NEON. `--stats` prints which engine ran
(`phases (sme2, int8 experts)`, `phases (sme2)` or `phases (vector)`).

Detection is at run time (`hw.optional.arm.FEAT_SME2` on macOS,
`AT_HWCAP2` on Linux, plus a check for the 512-bit streaming vectors the tile
layout assumes), so one binary built on any BF16 Mac (M2 or later) uses SME2
on an M4 and the BFDOT path elsewhere. clang builds the SME2 code into every
such binary through a per-function target region; GCC only builds it when
the whole target already has SME2 (its target pragma leaks SVE instructions
into the rest of the file, which faults on CPUs without SVE).

An M4 Max's SME units peak at ~4.1 TFLOPS bf16 in total (one per
performance cluster); the expert GEMMs sustain ~3.8 inside `pf`. Measured on
6k loghub lines (299k tokens), M4 Max, mean of two interleaved runs:

| Mode | norm+qkv | attn+router | experts | tok/s | lines/min |
|---|---:|---:|---:|---:|---:|
| `--exact` (BFDOT) | 5.7 s | 6.0 s | 40.5 s | 5,717 | 6,900 |
| `--no-int8` (SME2, bf16 experts) | 0.9 s | 1.2 s | 6.0 s | 36,138 | 43,500 |
| **default** (SME2, int8 experts) | 0.9 s | 1.3 s | 4.1 s | 46,851 | 56,400 |
| `--no-int8 --trim trim/w480.mask` | 0.9 s | 1.2 s | 4.6 s | 43,676 | 52,600 |
| `--trim trim/w480.mask` | 0.9 s | 1.3 s | 3.1 s | 55,243 | 66,500 |

Attention on SME matters more as documents get longer (attention windows
grow up to ±128 tokens); same machine, interleaved A/B against NEON
attention:

| Eval set (mean tokens/doc) | attn+router, NEON → SME | tok/s, NEON → SME |
|---|---:|---:|
| 6k loghub lines (50) | 1.87 → 1.70 s | 33,339 → 34,013 (1.02×) |
| 1k English (112) | 1.06 → 0.72 s | 29,795 → 32,772 (1.10×) |
| 1.5k Japanese (180) | 3.54 → 1.92 s | 26,734 → 32,453 (1.21×) |

SME2 rounds differently from the reference (bias added after accumulation,
different summation order, int8 experts), so it is near-exact rather than
byte-identical. Against `--exact` on held-out sets:

| Eval set | lines changed, default (`--no-int8`) | span F1 vs exact | char F1 vs gold: exact / `--no-int8` / default |
|---|---:|---:|---|
| 6k loghub lines | 2.3% (1.7%) | 0.982 | (no gold) |
| 1k English, PII-Masking-300k | 0.8% (0.8%) | 0.999 | 0.926 / 0.926 / 0.926 |
| 1.5k Japanese, openpii-1.5m ja + Sumi | 5.7% (4.0%) | 0.991 | 0.796 / 0.797 / 0.796 |

The changed documents are near-tie flips that land either way against the
gold labels: of the 78 Japanese docs where int8 and `--no-int8` disagree, 31
get closer to gold and 39 further (char F1 −0.0004, 95% bootstrap CI
−0.0008 to +0.0001); `--no-int8` against `--exact` splits 31 / 21. The log
set has no gold labels, so there only the agreement numbers are known. Use
`--exact` when you need the reference's output byte for byte. `--calib`
always runs bf16 experts; its stats agree with `--exact`'s to within the
BFDOT-vs-NEON noise floor.

### int8 experts

The expert GEMMs of layers 2-7 (75% of expert compute) run in int8 with
exact int32 accumulation: `SMOPA` on SME2, `SDOT` on NEON. Weights are
quantized at load (no extra files, same load time), per output column;
activations per row at run time, symmetric, scale max|v| / 127. Default on
SME2 chips; `--no-int8` turns it off, `--int8` turns it on elsewhere.

Why int8, measured on an M4 Max (16 cores):

| Engine | peak G(FL)OPS |
|---|---:|
| SME bf16 → fp32 (`BFMOPA`) | 4,800 |
| SME fp32 / fp16 → fp32 | 4,800 |
| SME int8 → int32 (`SMOPA`) | 9,700 |
| NEON int8 `SDOT` / `SMMLA`, 12 P-cores | 5,700 |
| NEON bf16 `BFDOT` / `BFMMLA`, 12 P-cores | 700 |

int8 is the only format the SME units run faster than bf16. Running both
engines at once peaked at 15.4 TOPS in a microbenchmark, but splitting
expert blocks between SME and NEON workers inside `pf` was never faster than
SME alone, so with SME2 every int8 GEMM goes to the SME units.

Plain int8 moved too many outputs (5.7% of log lines, 13% of Japanese
docs). Two changes bring it close to the bf16 SME path:

- **Hadamard rotation.** Both GEMM inputs are multiplied by an orthonormal
  Walsh-Hadamard transform along k first, and the weights by its transpose
  at load (exact in real arithmetic). That spreads outlier channels: a
  row's max/rms drops from 3.7-20 (expert input) and 10-17 (SwiGLU output) to
  the Gaussian ~3.3, so the 127 levels cover the bulk of the values.
- **Layers 0-1 stay bf16.** Quantizing layer 0 alone moves 3.4% of log
  lines; layer 1, 2.4%; layers 4-7 change nothing measurable. Early-layer
  error propagates through the rest of the network.

On the log set the experts phase drops from 6.0 to 4.1 s (1.30× overall)
and peak RSS from 5.4 to 4.5 GB. Without SME2 the default stays the
reference-exact BFDOT path; there `--int8` is an opt-in approximate mode.
On an M4 built with `-DPF_NO_SME` (standing in for M1-M3 / Graviton; that
hardware itself is untested) it takes 5,662 → 11,262 tok/s on logs, with
1.4% of log lines changed.

## Portability

One small kernel interface, chosen at compile time, plus one run-time choice:

- **SME2** — Apple M4 and later; built into every arm64 BF16 clang build and
  used when the CPU supports it (`--exact` opts out)
- **NEON + BFDOT** — Apple Silicon and AWS Graviton 3/4 (`-mcpu=native`)
- **AVX2 + FMA** — Intel / AMD (`-mavx2 -mfma`), same shift-widen bf16 trick
- **scalar C** — anything else

BFDOT, AVX2 and scalar produce byte-identical output (the AVX2 and scalar
builds are verified under Rosetta 2). Threading uses libdispatch on macOS and
a built-in pthread pool elsewhere; no other dependencies. Linux build:
`cc -O3 -std=c11 -march=native -pthread -o pf pf.c -lm`. `-DPF_NO_SME` builds
without the SME2 path. One binary for every BF16 Mac (M2 and later, SME2 on
M4+): `make CFLAGS="-O3 -std=c11 -Wall -Wextra -mcpu=apple-m2"`. `--int8`
works in every build: SME2 `SMOPA` on M4, NEON `SDOT` on any arm64 with the
dot-product extension (M1 and later, Graviton 2+), plain C elsewhere. The
three kernels accumulate in exact int32 and return identical results, so
`--int8` output differs between builds only where their dense paths do.

## Approximate modes

### Expert width trimming

`--trim MASK` keeps only the most important intermediate neurons of every
expert and re-packs the expert weights densely at load, so every MoE GEMM
shrinks by the same factor (experts are ~77% of the FLOPs). The shipped
`trim/w480.mask` keeps 480 of 640 neurons per expert (75% of expert compute).

Measured against the untrimmed model on an M4 Max (16 cores), held-out data:

| Eval set | lines changed | span F1 vs untrimmed | char F1 vs gold, untrimmed → trimmed |
|---|---:|---:|---|
| 6k loghub lines, 12 systems | 13.7% | 0.880 | (no gold) |
| 1k English, PII-Masking-300k | 5.2% | 0.991 | 0.926 → 0.926 |
| 1.5k Japanese, openpii-1.5m ja + Sumi | 28.1% | 0.944 | 0.796 → 0.797 |

Throughput on the log set is 5,182 → 6,491 tok/s on the `--exact` path
(1.25×; experts phase 1.34×), 36,138 → 43,676 tok/s with SME2 `--no-int8`
(1.21×) and 46,851 → 55,243 tok/s with the SME2 default (1.18×).
Changes are near-tie span flips, not lost coverage: accuracy against
gold labels is unchanged, and on logs the trimmed model emits about as many
spans as the full one (5,300 vs 5,249). Narrower masks trade more agreement
for speed (width 320: 1.56×, 21% of log lines changed, ~8% fewer log spans;
width 160: 2.2×). At equal speed, width trimming agreed with the full model
far better than top-k reduction on every set; dropping whole experts gave no
speedup at all (each token still runs four). Like `--skip-beta`, it is **not**
output-preserving: validate on your own corpus before enabling.

Build a mask for your own traffic (one stats file per language/domain;
files are weighted equally; width must be a multiple of 8):

```sh
./pf --lines --calib en.bin   -f english.txt  > /dev/null
./pf --lines --calib ja.bin   -f japanese.txt > /dev/null
./pf --lines --calib logs.bin -f logs.txt     > /dev/null
python3 trim.py my.mask 480 en.bin ja.bin logs.bin
```

Calibrate on every language you serve: a logs-only mask roughly doubled the
Japanese disagreement in our tests. The shipped mask was calibrated on 6k
loghub lines, 500 PII-Masking-300k English rows, and 1.3k Japanese texts
(openpii-1.5m ja + Sumi train), disjoint from the eval sets above.

### Expert skipping

`--skip-beta B` enables dynamic expert skipping (Lu et al. 2024): expert
slots whose routing weight is below `B x` the top slot's are dropped and the
rest renormalized. Measured on this model: it is **not** output-preserving at
any useful threshold (even B=0.02 flips ~8% of dense-PII docs, mostly span
boundaries on near-tie tokens; B=0.6 is ~30% faster and flips ~8% of short
docs). Default off; treat it as an accuracy/speed dial and evaluate on your
own corpus before enabling.

Categories: `account_number`, `private_address`, `private_date`,
`private_email`, `private_person`, `private_phone`, `private_url`, `secret`.
